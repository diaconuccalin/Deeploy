## Project Overview

**Deeploy** is an ONNX-to-C compiler that generates low-level optimized C code for multi-cluster, heterogeneous System-on-Chips (SoCs). It enables configurable deployment flows from a bottom-up compiler perspective, modeling target hardware in a fine-grained and modular manner.

### Key Characteristics

- **Input**: ONNX neural network models
- **Output**: Optimized C code for embedded systems
- **Target Hardware**: Heterogeneous SoCs (PULP clusters, Neureka accelerators, Cortex-M, etc.)
- **Focus**: Energy-efficient deployment of DNNs on resource-constrained devices

### Supported Platforms

1. **Generic CPU** - Host machine (no tiling)
2. **CortexM Processors** - ARM Cortex-M4 via QEMU
3. **MemPool + ITA** - Custom RISC-V cluster with Integer Tensor Accelerator
4. **Siracusa** - Multi-cluster PULP platform with optional Neureka accelerator
5. **Snitch Cluster** - High-efficiency RISC-V cluster
6. **SoftHier** - Software hierarchy platform
7. **Chimera** - Custom heterogeneous platform

## Architecture

### High-Level Flow

```
PyTorch/TensorFlow Model → ONNX → Deeploy → Optimized C Code → Target Binary
                                      ↓
                              Type Inference
                              Optimization Passes
                              Memory Management
                              Tiling (Optional)
                              Code Generation
```

### Core Components

1. **Deployers** (`Deeploy/Targets/*/Deployer.py`)
   - Platform-specific deployment logic
   - Orchestrate compilation pipeline
   - Apply optimization passes

2. **Platforms** (`Deeploy/Targets/*/Platform.py`)
   - Hardware modeling
   - Engine definitions (CPU cores, accelerators)
   - Memory hierarchy specifications

3. **Parsers** (`Deeploy/Targets/*/Parsers.py`)
   - ONNX operator parsing
   - Node type checking
   - Graph transformations

4. **Bindings** (`Deeploy/Targets/*/Bindings.py`)
   - C function bindings for operators
   - Platform-specific implementations

5. **Tiling Extension** (`Deeploy/TilingExtension/`)
   - Memory-aware tiling
   - Buffer management
   - DMA scheduling

6. **Memory Level Extension** (`Deeploy/MemoryLevelExtension/`)
   - Multi-level memory management
   - Data placement optimization

## Test Structure

Tests are located in `DeeployTest/Tests/` with each test in its own directory.

### Required Test Files

Each test directory must contain:

1. **network.onnx** - The ONNX model file
   - Standard ONNX format
   - Can be created from PyTorch, TensorFlow, or onnx_graphsurgeon

2. **inputs.npz** - Test input data (NumPy archive)
   - Contains named arrays (e.g., `input_0`, `input_1`, ...)
   - Keys should match ONNX input names
   - Data type: typically float32 or float64

3. **outputs.npz** - Expected output data (NumPy archive)
   - Contains named arrays (e.g., `output_0`, `output_1`, ...)
   - Generated by running the model with the test inputs
   - Used for correctness verification

4. **activations.npz** (Optional) - Intermediate activations
   - For debugging and verification
   - Contains intermediate layer outputs
   - Useful for identifying where computation diverges

### Test Directory Example

```
DeeployTest/Tests/testFloatGEMM/
├── network.onnx      # ONNX model
├── inputs.npz        # Test inputs
└── outputs.npz       # Expected outputs

DeeployTest/Tests/simpleCNN/
├── network.onnx      # ONNX model
├── inputs.npz        # Test inputs
├── outputs.npz       # Expected outputs
└── activations.npz   # Intermediate activations (optional)
```

### Understanding .npz Files

NPZ files are NumPy archives containing multiple arrays:

```python
import numpy as np

# Loading
inputs = np.load('inputs.npz')
for key in inputs.files:
    print(f"{key}: shape={inputs[key].shape}, dtype={inputs[key].dtype}")

# Creating
np.savez('inputs.npz',
         input_0=np.random.randn(1, 3, 224, 224).astype(np.float32))
```

### Test Execution Flow

1. **Code Generation** (`DeeployTest/generateNetwork.py`)
   - Loads ONNX model and test data
   - Infers data types and quantization offsets
   - Generates platform-specific C code
   - Output: C files in `DeeployTest/TEST_<PLATFORM>/`

2. **Compilation** (handled by test runners)
   - Uses platform-specific toolchain
   - Builds executable from generated C code
   - Links with platform libraries

3. **Execution** (simulator or host)
   - Runs compiled binary
   - Captures output
   - Compares against expected outputs

4. **Verification**
   - Checks numerical correctness
   - Reports errors if outputs don't match

## Development Workflows

### Running Tests

#### Single Test on Specific Platform

```bash
cd DeeployTest
python testRunner_generic.py -t Tests/Adder
python testRunner_siracusa.py -t Tests/testMatMul --cores=8
```

#### Tiled Test (Memory-Constrained)

```bash
python testRunner_tiled_siracusa.py -t Tests/testMatMul --cores=8 --l1=16000 --l2=128000
```

#### With Debugging

```bash
python testRunner_generic.py -t Tests/Adder -vvv --debug
```

### Test Runner Arguments

Common arguments across all test runners:

- `-t <dir>` - Test directory (required)
- `-p <platform>` - Target platform
- `-d <dir>` - Output dump folder (default: ./TestFiles)
- `-v`, `-vv`, `-vvv` - Verbosity levels (more v's = more verbose)

Tiling-specific arguments:

- `--l1 <bytes>` - L1 memory size
- `--l2 <bytes>` - L2 memory size
- `--doublebuffer` - Enable double buffering
- `--defaultMemLevel` - Default memory level for allocations
- `--cores <n>` - Number of cores to use

### Creating a New Test

#### Method 1: Manual Creation (Current Approach)

1. Create test directory: `mkdir DeeployTest/Tests/mytest`
2. Generate ONNX model (using PyTorch, ONNX, or onnx_graphsurgeon)
3. Create test inputs and compute expected outputs
4. Save files as network.onnx, inputs.npz, outputs.npz
5. Run test to verify

#### Method 2: Automated Script (See `create_deeploy_test.py`)

The new test generation script automates this process (see below).

### Inspecting Generated Code

After running a test, examine the generated code:

```bash
# Example: Check generated code for Siracusa platform
cat DeeployTest/TEST_SIRACUSA/Tests/testMatMul/Network.c
```

Key files to inspect:

- `Network.c` - Main network execution code
- `Network.h` - Network header with type definitions
- `main.c` - Test harness
- `CMakeLists.txt` - Build configuration

## Common Tasks

### Adding Support for a New ONNX Operator

1. **Define Parser** (in `Deeploy/Targets/<platform>/Parsers.py`)
   ```python
   @_Parsers.register
   class MyOpParser(NodeParser):
       def parse(self, node, ctxt):
           # Parse node attributes
           # Create binding
   ```

2. **Create Binding** (in `Deeploy/Targets/<platform>/Bindings.py`)
   ```python
   class MyOpBinding(BasicBinding):
       def __init__(self, ...):
           # Define inputs, outputs, local variables
   ```

3. **Add Tests** - Create test case in `DeeployTest/Tests/`

### Modifying an Optimization Pass

Optimization passes are in `Deeploy/CommonExtensions/OptimizationPasses/`

```python
class MyOptimizationPass(OptimizationPass):
    def apply(self, ctxt):
        # Modify the graph
        return modified_graph
```

### Adding a New Platform

1. Create directory: `Deeploy/Targets/MyPlatform/`
2. Implement required modules:
   - `Platform.py` - Hardware model
   - `Deployer.py` - Deployment orchestration
   - `Parsers.py` - Operator parsing
   - `Bindings.py` - C code bindings
3. Create test runner: `DeeployTest/testRunner_myplatform.py`
4. Add CI configuration

## Test Generation Script

A new standalone script `create_deeploy_test.py` has been added to automate test creation from PyTorch models.

### Usage

```bash
# Basic usage
python create_deeploy_test.py \
    --model-path models/my_model.py \
    --model-class MyModel \
    --test-name testMyModel \
    --input-shapes "1,3,224,224"

# With multiple inputs
python create_deeploy_test.py \
    --model-path models/my_model.py \
    --model-class MyModel \
    --test-name testMyModel \
    --input-shapes "1,512" "1,512"

# With custom input range and seed
python create_deeploy_test.py \
    --model-path models/my_model.py \
    --model-class MyModel \
    --test-name testMyModel \
    --input-shapes "1,3,32,32" \
    --input-range -1.0 1.0 \
    --seed 42
```

### What It Does

1. Loads PyTorch model
2. Generates random test inputs
3. Runs forward pass to get expected outputs
4. Exports model to ONNX
5. Saves inputs.npz and outputs.npz
6. Creates test directory structure

### Script Features

- Automatic ONNX export from PyTorch
- Random input generation with configurable ranges
- Reproducible tests (via seed)
- Support for multiple inputs
- Input/output validation
- Error handling and helpful messages

## Troubleshooting

### Common Issues

#### 1. ONNX Export Fails

**Symptoms**: Error during ONNX export
**Solutions**:
- Ensure PyTorch model is in eval mode
- Check for unsupported operations
- Try `opset_version=14` or newer
- Use `torch.onnx.export` verbose mode

#### 2. Type Inference Issues

**Symptoms**: Generated code has wrong types
**Solutions**:
- Use `--input-type-map` to override types
- Check input data ranges
- Ensure signedness is correctly inferred

#### 3. Memory Allocation Errors (Tiled Tests)

**Symptoms**: Test fails with memory errors
**Solutions**:
- Increase L1/L2 sizes
- Check tiling configuration
- Review memory allocation strategy (`--memAllocStrategy`)

#### 4. Numerical Mismatch

**Symptoms**: Output doesn't match expected
**Solutions**:
- Check quantization settings
- Verify input preprocessing
- Enable debug mode to inspect intermediate activations
- Compare with ONNX runtime output

#### 5. Compilation Errors

**Symptoms**: Generated C code doesn't compile
**Solutions**:
- Check platform-specific toolchain
- Verify generated code structure
- Review binding implementations

### Debugging Strategies

#### Enable Verbose Logging

```bash
python testRunner_generic.py -t Tests/mytest -vvv
```

#### Inspect ONNX Graph

Use Netron to visualize:
```bash
# Install netron
pip install netron

# View model
netron Tests/mytest/network.onnx
```

#### Check Generated Code

```bash
# Look at generated C code
cat DeeployTest/TEST_GENERIC/Tests/mytest/Network.c

# Check for specific patterns
grep -n "GEMM" DeeployTest/TEST_GENERIC/Tests/mytest/Network.c
```

#### Run ONNX Runtime for Comparison

```python
import onnx
import onnxruntime as ort
import numpy as np

# Load model
session = ort.InferenceSession('network.onnx')

# Load inputs
inputs = np.load('inputs.npz')
input_dict = {session.get_inputs()[i].name: inputs[f'input_{i}']
              for i in range(len(session.get_inputs()))}

# Run inference
outputs = session.run(None, input_dict)

# Compare with expected
expected = np.load('outputs.npz')
for i, out in enumerate(outputs):
    exp = expected[f'output_{i}']
    print(f"Output {i} - Max diff: {np.max(np.abs(out - exp))}")
```

## Best Practices

### When Creating Tests

1. **Use Meaningful Names**: `testFloatGEMM`, not `test1`
2. **Keep Tests Small**: Focus on specific functionality
3. **Document Complex Tests**: Add README in test directory
4. **Version Control**: Commit test scripts, not just artifacts
5. **Test Multiple Platforms**: Verify cross-platform compatibility

### When Modifying Core Code

1. **Run Regression Tests**: Test multiple platforms
2. **Document Changes**: Update docstrings and comments
3. **Follow Code Style**: Use `yapf` and `isort`
4. **Check Type Safety**: Verify type inference still works
5. **Update Documentation**: Keep CLAUDE.md in sync

### When Adding Features

1. **Start with Tests**: Create test cases first
2. **Incremental Development**: Small, testable changes
3. **Platform Agnostic**: Use common extensions when possible
4. **Performance Aware**: Profile and optimize
5. **Document Limitations**: Note platform-specific constraints
